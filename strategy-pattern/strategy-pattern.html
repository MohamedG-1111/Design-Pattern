Strategy Design Pattern

شرح بالمصري، خطوة خطوة، بأمثلة C# عملية — وإزاي يفترق عن Factory و Adapter و Decorator.

الجزء الأول: Strategy الجزء التاني: Strategy vs Factory

الجزء الأول: Strategy Pattern من الصفر

1. يعني إيه Strategy Pattern؟

كلمة Strategy معناها «استراتيجية» أو «طريقة».

الفكرة ببساطة: عندنا عملية ممكن تتنفذ بأكتر من طريقة، وعايزين نقدر نغيّر الطريقة المستخدمة من غير ما نغيّر الكلاس الأساسي اللي بيستخدمها.

2. المشكلة اللي بنحلها

تخيل إن عندنا تطبيق توصيل طلبات، والعميل يقدر يختار طريقة حساب تكلفة الشحن:

  • الشحن العادي (Standard).
  • الشحن السريع (Express).
  • الشحن المجاني (Free).

ممكن في البداية نكتب الكود بالشكل ده:

public class ShippingService
{
    public decimal CalculateShipping(string shippingType)
    {
        if (shippingType == "Standard")
        {
            return 30;
        }
        else if (shippingType == "Express")
        {
            return 60;
        }
        else if (shippingType == "Free")
        {
            return 0;
        }

        throw new Exception("Invalid shipping type");
    }
}

ونستخدمه كده:

var shippingService = new ShippingService();

decimal cost = shippingService.CalculateShipping("Express");

Console.WriteLine(cost);
60

3. إيه المشكلة في الكود ده؟

الكود شغال، لكن تخيل إن الشركة قررت تضيف:

  • Same Day Shipping.
  • International Shipping.
  • Weekend Shipping.

هنضطر نرجع نعدّل ShippingService ونضيف شروط جديدة. وده مع الوقت هيعمل مشاكل:

  1. الكلاس هيكبر جدًا.
  2. كل طريقة شحن جديدة هتحتاج تعديل في نفس الكلاس.
  3. احتمالية حدوث أخطاء في الطرق القديمة هتزيد.
  4. الكلاس هيبقى مسؤول عن تفاصيل طرق شحن كتير.

بدل ما نخلي ShippingService يعرف كل طرق الشحن، هنفصل كل طريقة في كلاس مستقل.

4. الحل باستخدام Strategy Pattern

الفكرة إننا هنعمل Interface يمثل الاستراتيجية المشتركة بين كل طرق الشحن.

الخطوة الأولى: إنشاء Interface

public interface IShippingStrategy
{
    decimal CalculateShipping();
}
الـ Interface بيقول إن أي طريقة شحن لازم يكون عندها Method اسمها CalculateShipping، لكن مش بيحدد طريقة الحساب نفسها.

الخطوة الثانية: إنشاء الاستراتيجيات المختلفة

public class StandardShipping : IShippingStrategy
{
    public decimal CalculateShipping() { return 30; }
}

public class ExpressShipping : IShippingStrategy
{
    public decimal CalculateShipping() { return 60; }
}

public class FreeShipping : IShippingStrategy
{
    public decimal CalculateShipping() { return 0; }
}

دلوقتي كل طريقة شحن بقت موجودة في كلاس مستقل.

الخطوة الثالثة: الكلاس المسؤول عن استخدام الاستراتيجية

public class ShippingService
{
    private readonly IShippingStrategy _shippingStrategy;

    public ShippingService(IShippingStrategy shippingStrategy)
    {
        _shippingStrategy = shippingStrategy;
    }

    public decimal CalculateShipping()
    {
        return _shippingStrategy.CalculateShipping();
    }
}

أولًا: private readonly IShippingStrategy _shippingStrategy; — إحنا بنقول إن ShippingService هيحتفظ باستراتيجية شحن. لكن استخدمنا Interface مش Class معين، يعني الكلاس مش فارق معاه الطريقة Standard ولا Express ولا Free.

ثانيًا: الـ Constructor — بنبعت طريقة الشحن من بره. يعني اللي بيعمل Object من ShippingService هو اللي بيحدد طريقة الشحن.

ثالثًا: return _shippingStrategy.CalculateShipping(); — بننفذ الطريقة اللي اتبعتت لنا. لو اتبعت ExpressShipping هينفذ حساب الشحن السريع، ولو اتبعت StandardShipping هينفذ حساب الشحن العادي. وده جوهر الـ Strategy Pattern.

5. نجرب الكود

class Program
{
    static void Main()
    {
        IShippingStrategy strategy = new ExpressShipping();

        ShippingService shippingService =
            new ShippingService(strategy);

        decimal cost = shippingService.CalculateShipping();

        Console.WriteLine($"Shipping Cost: {cost}");
    }
}
Shipping Cost: 60

لو عايزين نغيّر طريقة الشحن، كل اللي هنعمله إننا نغيّر الاستراتيجية:

IShippingStrategy strategy = new StandardShipping();

ShippingService shippingService =
    new ShippingService(strategy);

Console.WriteLine(shippingService.CalculateShipping());
30

من غير ما نغيّر سطر واحد داخل ShippingService!

7. إمتى أستخدم Strategy Pattern؟

  • يكون عندك أكتر من طريقة لتنفيذ نفس العملية.
  • تكون محتاج تغيّر طريقة التنفيذ حسب اختيار المستخدم.
  • تلاقي نفسك بتكرر if / else أو switch لاختيار سلوك مختلف.
  • عايز تضيف سلوك جديد من غير تعديل الكلاس الأساسي.

أمثلة حقيقية في مشاريع .NET:

  • طرق الدفع: Cash / Visa / PayPal.
  • طرق الخصم: Percentage / Fixed Amount.
  • طرق حساب الضريبة.
  • طرق إرسال الإشعارات.
  • طرق حساب أسعار الشحن.

9. اختبر فهمك

عندنا تطبيق بيدعم طرق دفع مختلفة: Cash و Visa و PayPal. وعايزين نضيف طريقة دفع جديدة من غير ما نعدّل PaymentService. إيه أنسب حل؟

الخلاصة: بدل ما الكلاس يعرف كل الطرق الممكنة لتنفيذ العملية، بنخليه يعتمد على Interface، ونبعتله الطريقة اللي عايزينه يستخدمها. ده هو الـ Strategy Pattern.

الجزء التاني: الفرق بين Strategy و Factory

الـ Strategy ممكن تحس إنه شبه الـ Simple Factory والـ Factory Method، لأن التلاتة فيهم Interface وكذا Class بيعملوا Implement ليه. لكن الفرق الأساسي مش في شكل الكود، الفرق في المشكلة اللي كل Pattern بيحلها. هنستخدم مثال طرق الدفع.

1. Simple Factory – أنا عايز أنشئ Object

public interface IPayment
{
    void Pay(decimal amount);
}

public class CashPayment : IPayment
{
    public void Pay(decimal amount) { Console.WriteLine("Cash Payment"); }
}

public class VisaPayment : IPayment
{
    public void Pay(decimal amount) { Console.WriteLine("Visa Payment"); }
}

الـ Simple Factory مسؤولة عن إنشاء الـ Object المناسب:

public class PaymentFactory
{
    public static IPayment CreatePayment(string type)
    {
        if (type == "Cash")
            return new CashPayment();

        if (type == "Visa")
            return new VisaPayment();

        throw new Exception("Invalid Payment Type");
    }
}

الاستخدام:

IPayment payment = PaymentFactory.CreatePayment("Visa");

payment.Pay(100);

الفكرة: أنا مش عايز أعرف إزاي أعمل new VisaPayment() أو new CashPayment()، فبخلي Factory تنشئ الـ Object المناسب.

2. Factory Method – كل Factory متخصصة في إنشاء Object

بدل ما يكون عندي Factory واحدة فيها شروط، بعمل Factory Base Class، وكل Factory متخصصة تحدد هتنشئ أنهي نوع.

public abstract class PaymentFactory
{
    public abstract IPayment CreatePayment();
}

public class CashPaymentFactory : PaymentFactory
{
    public override IPayment CreatePayment()
    {
        return new CashPayment();
    }
}

public class VisaPaymentFactory : PaymentFactory
{
    public override IPayment CreatePayment()
    {
        return new VisaPayment();
    }
}

الاستخدام:

PaymentFactory factory = new VisaPaymentFactory();

IPayment payment = factory.CreatePayment();

payment.Pay(100);

الفكرة: أنا بفصل قرار إنشاء الـ Object في Factory متخصصة، وكل Factory بتحدد نوع الـ Object اللي هتنشئه.

3. Strategy – أنا عايز أغيّر طريقة تنفيذ العملية

هنا الهدف مختلف. مشكلتي مش إنشاء Object، مشكلتي إن عندي أكتر من طريقة لتنفيذ عملية الدفع.

public interface IPaymentStrategy
{
    void Pay(decimal amount);
}

public class CashPayment : IPaymentStrategy
{
    public void Pay(decimal amount)
    {
        Console.WriteLine($"Paid {amount} using Cash");
    }
}

public class VisaPayment : IPaymentStrategy
{
    public void Pay(decimal amount)
    {
        Console.WriteLine($"Paid {amount} using Visa");
    }
}

نعمل كلاس بيستخدم الاستراتيجية:

public class PaymentService
{
    private readonly IPaymentStrategy _strategy;

    public PaymentService(IPaymentStrategy strategy)
    {
        _strategy = strategy;
    }

    public void Pay(decimal amount)
    {
        _strategy.Pay(amount);
    }
}

الاستخدام:

IPaymentStrategy strategy = new VisaPayment();

PaymentService service = new PaymentService(strategy);

service.Pay(100);

الفكرة: PaymentService مش محتاج يعرف تفاصيل الدفع بالفيزا أو الكاش، هو بس بيستخدم الاستراتيجية اللي اتبعتتله.

4. الفرق الجوهري بينهم

  • Simple Factory — مين هيعمل الـ Object؟ Factory بتختار وتنشئ الـ Object المناسب.
  • Factory Method — أنهي Factory هتنشئ الـ Object؟ كل Concrete Factory بتحدد نوع الـ Object اللي هتنشئه.
  • Strategy — هننفذ العملية إزاي؟ كل Strategy بتقدم طريقة مختلفة لتنفيذ نفس العملية.

5. هل ممكن نستخدم Factory و Strategy مع بعض؟

أيوه! ودي نقطة مهمة جدًا في المشاريع الحقيقية. مثلًا المستخدم اختار Visa، فالـ Factory تنشئ VisaPayment، وبعدها نمرر الـ Object ده إلى PaymentService باعتباره Strategy.

IPaymentStrategy strategy =
    PaymentFactory.CreatePayment("Visa");

PaymentService service =
    new PaymentService(strategy);

service.Pay(100);
  1. الـ Factory مسؤولة عن إنشاء الـ Object.
  2. الـ Strategy مسؤولة عن تنفيذ طريقة الدفع.
  3. الـ PaymentService بيستخدم الاستراتيجية من غير ما يعرف تفاصيلها.
الـ Factory مش بديل للـ Strategy، وممكن تستخدم الاتنين مع بعض لأن كل واحد بيحل مشكلة مختلفة.
