أولًا: نفهم المشكلة اللي الـ Factory بتحلها

تخيل إن عندك Order Service في مشروع E-commerce، والمسؤول عن إرسال إشعار للعميل بعد ما يعمل Order. عندك 3 طرق للإشعار:

  • Email
  • SMS
  • WhatsApp

ممكن تكتب الكود بالشكل ده:

public class OrderService
{
    public void PlaceOrder(string notificationType)
    {
        if (notificationType == "Email")
        {
            var email = new EmailNotification();
            email.Send();
        }
        else if (notificationType == "SMS")
        {
            var sms = new SmsNotification();
            sms.Send();
        }
        else if (notificationType == "WhatsApp")
        {
            var whatsapp = new WhatsAppNotification();
            whatsapp.Send();
        }
    }
}

الكود شغال، لكن عندنا مشاكل:

  1. OrderService مسؤول عن تنفيذ الـ Order وعن إنشاء أنواع الإشعارات.
  2. كل ما نضيف نوع جديد، لازم نعدل OrderService.
  3. عندنا ارتباط قوي (Tight Coupling) بين OrderService والـ Classes الخاصة بالإشعارات.
  4. صعب نختبر OrderService بشكل مستقل.
الهدف: نخلي OrderService يتعامل مع Interface بدل ما يعرف كل Class بيتم إنشاؤه إزاي. يعني نفصل عملية إنشاء الـ Objects عن الكود اللي بيستخدمها.

1. Simple Factory

Class واحدة مسؤولة عن إنشاء Objects

الـ Simple Factory عبارة عن Class بنحط فيها منطق إنشاء الـ Objects، والـ Client بيطلب منها الـ Object اللي محتاجه. بدل ما OrderService يعمل new EmailNotification() بنفسه، هنخلي Factory هي اللي تعمل كده.

الخطوة الأولى: نعمل Interface

public interface INotification
{
    void Send();
}

كل أنواع الإشعارات هتطبق الـ Interface دي.

الخطوة الثانية: نعمل Implementations

public class EmailNotification : INotification
{
    public void Send()
    {
        Console.WriteLine("Sending Email...");
    }
}
public class SmsNotification : INotification
{
    public void Send()
    {
        Console.WriteLine("Sending SMS...");
    }
}
public class WhatsAppNotification : INotification
{
    public void Send()
    {
        Console.WriteLine("Sending WhatsApp...");
    }
}

الخطوة الثالثة: نعمل Simple Factory

public class NotificationFactory
{
    public static INotification Create(string type)
    {
        switch (type)
        {
            case "Email":
                return new EmailNotification();

            case "SMS":
                return new SmsNotification();

            case "WhatsApp":
                return new WhatsAppNotification();

            default:
                throw new ArgumentException("Invalid notification type");
        }
    }
}

خلي بالك: الـ Factory بترجع INotification مش EmailNotification أو SmsNotification.

ليه؟ لأن كل الـ Classes بتطبق نفس الـ Interface، وبالتالي الـ Client مش محتاج يعرف نوع الـ Object الحقيقي.

الخطوة الرابعة: نستخدم الـ Factory في OrderService

public class OrderService
{
    public void PlaceOrder(string notificationType)
    {
        INotification notification =
            NotificationFactory.Create(notificationType);

        notification.Send();
    }
}

دلوقتي إيه اللي حصل؟

OrderServiceيطلب Notification من الـ Factory
↓
NotificationFactoryتقرر أنهي Object يتم إنشاؤه

إيه اللي اتحسن؟

  • OrderService مش مسؤول عن إنشاء الـ Objects.
  • منطق الإنشاء أصبح في مكان واحد.
  • التعامل بقى من خلال Interface.

لكن فيه مشكلة لسه موجودة

كل ما نضيف Notification جديدة، لازم نعدل NotificationFactory ونضيف Case جديدة في الـ Switch. وده معناه إن الـ Factory نفسها بتتغير كل ما نضيف نوع جديد. وهنا نيجي للمرحلة التانية.

ملحوظة مصطلحية: Simple Factory أسلوب شائع لتنظيم إنشاء الـ Objects، لكنه مش واحد من الـ GoF Design Patterns الرسمية المعروفة باسم Factory Method وAbstract Factory.

2. Factory Method

الـ Subclasses هي اللي تقرر هتنشئ أنهي Object

خلينا نفتكر المشكلة في Simple Factory: كل ما نضيف نوع جديد بنعدل الـ Factory. الـ Factory Method بيحل المشكلة دي عن طريق استخدام الـ Inheritance والـ Polymorphism.

بدل ما يكون عندنا Factory واحدة فيها Switch، هنعمل Factory Base Class، وكل نوع هيكون له Factory خاصة بيه.

الخطوة الأولى: الـ Product Interface

public interface INotification
{
    void Send();
}

الخطوة الثانية: المنتجات المختلفة

public class EmailNotification : INotification
{
    public void Send()
    {
        Console.WriteLine("Sending Email...");
    }
}
public class SmsNotification : INotification
{
    public void Send()
    {
        Console.WriteLine("Sending SMS...");
    }
}

الخطوة الثالثة: نعمل Abstract Creator

public abstract class NotificationCreator
{
    public abstract INotification CreateNotification();

    public void SendNotification()
    {
        INotification notification = CreateNotification();
        notification.Send();
    }
}

ركز معايا هنا. عندنا Method اسمها:

public abstract INotification CreateNotification();

دي اسمها Factory Method. يعني الـ Base Class بتقول: أنا محتاجة حد ينشئلي Notification، لكن مش هحدد هتكون Email ولا SMS. الـ Subclasses هي اللي هتحدد.

وفي نفس الوقت عندنا:

public void SendNotification()
{
    INotification notification = CreateNotification();
    notification.Send();
}

الـ Base Class بتستخدم الـ Object، من غير ما تعرف نوعه الحقيقي.

الخطوة الرابعة: نعمل Concrete Creators

Factory خاصة بالـ Email:

public class EmailNotificationCreator : NotificationCreator
{
    public override INotification CreateNotification()
    {
        return new EmailNotification();
    }
}

Factory خاصة بالـ SMS:

public class SmsNotificationCreator : NotificationCreator
{
    public override INotification CreateNotification()
    {
        return new SmsNotification();
    }
}

الخطوة الخامسة: الاستخدام

NotificationCreator creator = new EmailNotificationCreator();
creator.SendNotification();

الـ Output:

Sending Email...

ولو عايز SMS:

NotificationCreator creator = new SmsNotificationCreator();
creator.SendNotification();

الـ Output:

Sending SMS...

نفهم الـ Factory Method بصريًا

NotificationCreator (Abstract)يحتوي على CreateNotification() وSendNotification()
↓

ملحوظة مهمة: Factory Method مش معناها إننا عملنا Method اسمها Factory وخلاص. الفكرة الأساسية إن الـ Base Creator يعرّف Method لإنشاء المنتج، والـ Subclasses تعمل Override ليها وتحدد المنتج المطلوب.

3. Abstract Factory

إنشاء عائلات من Objects مرتبطة ببعض

ده أهم اختلاف بين Factory Method وAbstract Factory. خلينا نستخدم مثال من E-commerce.

تخيل إن عندك Application بيدعم نوعين من أنظمة الدفع: Stripe وPayPal. وكل نظام دفع عنده حاجتين:

  1. Payment Processor: المسؤول عن تنفيذ عملية الدفع.
  2. Payment Validator: المسؤول عن التحقق من بيانات الدفع.

يعني عندنا عائلتين من الـ Objects:

Stripe Family

StripePaymentProcessorتنفيذ الدفع
StripePaymentValidatorالتحقق من الدفع

PayPal Family

PayPalPaymentProcessorتنفيذ الدفع
PayPalPaymentValidatorالتحقق من الدفع

المشكلة هنا إننا مش عايزين ننشئ Processor من Stripe ونستخدم معاه Validator من PayPal بالغلط. عايزين Factory تضمن إننا ننشئ Objects من نفس العائلة. وده بالضبط دور Abstract Factory.

الخطوة الأولى: نعمل Interfaces للـ Products

أول Product مسؤول عن الدفع:

public interface IPaymentProcessor
{
    void Pay(decimal amount);
}

ثاني Product مسؤول عن التحقق:

public interface IPaymentValidator
{
    bool Validate();
}

الخطوة الثانية: نعمل Implementations

Stripe:

public class StripePaymentProcessor : IPaymentProcessor
{
    public void Pay(decimal amount)
    {
        Console.WriteLine($"Stripe paid: {amount}");
    }
}
public class StripePaymentValidator : IPaymentValidator
{
    public bool Validate()
    {
        Console.WriteLine("Validating Stripe payment");
        return true;
    }
}

PayPal:

public class PayPalPaymentProcessor : IPaymentProcessor
{
    public void Pay(decimal amount)
    {
        Console.WriteLine($"PayPal paid: {amount}");
    }
}
public class PayPalPaymentValidator : IPaymentValidator
{
    public bool Validate()
    {
        Console.WriteLine("Validating PayPal payment");
        return true;
    }
}

الخطوة الثالثة: نعمل Abstract Factory

في Factory Method كان عندنا Method واحدة لإنشاء Product. لكن في Abstract Factory ممكن يكون عندنا أكتر من Factory Method، كل واحدة مسؤولة عن إنشاء Product مختلف.

public interface IPaymentFactory
{
    IPaymentProcessor CreatePaymentProcessor();
    IPaymentValidator CreatePaymentValidator();
}

الـ Interface دي بتقول: أي Factory هتطبقها لازم توفر طريقتين لإنشاء:

  • Payment Processor
  • Payment Validator

الخطوة الرابعة: نعمل Concrete Factories

Stripe Factory:

public class StripePaymentFactory : IPaymentFactory
{
    public IPaymentProcessor CreatePaymentProcessor()
    {
        return new StripePaymentProcessor();
    }

    public IPaymentValidator CreatePaymentValidator()
    {
        return new StripePaymentValidator();
    }
}

PayPal Factory:

public class PayPalPaymentFactory : IPaymentFactory
{
    public IPaymentProcessor CreatePaymentProcessor()
    {
        return new PayPalPaymentProcessor();
    }

    public IPaymentValidator CreatePaymentValidator()
    {
        return new PayPalPaymentValidator();
    }
}

لاحظ إن كل Factory بتنشئ عائلة كاملة متوافقة مع بعضها.

الخطوة الخامسة: نستخدم Abstract Factory

نعمل Payment Service:

public class PaymentService
{
    private readonly IPaymentProcessor _processor;
    private readonly IPaymentValidator _validator;

    public PaymentService(IPaymentFactory factory)
    {
        _processor = factory.CreatePaymentProcessor();
        _validator = factory.CreatePaymentValidator();
    }

    public void ProcessPayment(decimal amount)
    {
        if (!_validator.Validate())
        {
            throw new Exception("Invalid payment");
        }

        _processor.Pay(amount);
    }
}

لاحظ إن PaymentService مش عارف هل بيستخدم Stripe أو PayPal. هو بيتعامل مع Interfaces فقط.

الاستخدام مع Stripe:

IPaymentFactory factory = new StripePaymentFactory();
var paymentService = new PaymentService(factory);
paymentService.ProcessPayment(1000);

الاستخدام مع PayPal:

IPaymentFactory factory = new PayPalPaymentFactory();
var paymentService = new PaymentService(factory);
paymentService.ProcessPayment(1000);

في الحالتين، PaymentService نفسه لم يتغير.

الفرق الجوهري بين الثلاثة

دي أهم نقطة محتاج تكون فاهمها كويس:

1. Simple Factory

منتج واحد من اختيارات متعددة

Factory واحدة تختار المنتج المطلوب.

مثال:

Email أو SMS أو WhatsApp.

2. Factory Method

الـ Subclass تحدد المنتج

كل Concrete Creator مسؤول عن إنشاء نوع معين من المنتجات.

مثال:

EmailNotificationCreator وSmsNotificationCreator.

3. Abstract Factory

عائلة كاملة من المنتجات

Factory واحدة تنشئ مجموعة Objects مترابطة ومتوافقة.

مثال:

Stripe Processor + Stripe Validator.

رابعًا: إزاي نستخدم الكلام ده في ASP.NET Core؟

دي نقطة مهمة جدًا لأنك هتقابل الـ Factories في مشاريع .NET الحقيقية.

في ASP.NET Core عندنا Dependency Injection Container، وممكن نسجل الـ Implementations بالشكل ده:

builder.Services.AddScoped<IPaymentFactory, StripePaymentFactory>();
builder.Services.AddScoped<PaymentService>();

وبالتالي لما تطلب PaymentService، الـ DI هتعمل Inject للـ StripePaymentFactory تلقائيًا.

لكن تخيل إنك عايز تختار بين Stripe وPayPal حسب إعدادات الشركة أو الطلب. هنا ممكن تستخدم Factory مع DI:

public class PaymentFactory : IPaymentFactory
{
    private readonly IServiceProvider _serviceProvider;

    public PaymentFactory(IServiceProvider serviceProvider)
    {
        _serviceProvider = serviceProvider;
    }

    public IPaymentProcessor CreatePaymentProcessor()
    {
        // اختيار الـ Processor حسب الإعدادات
        return _serviceProvider
            .GetRequiredService<StripePaymentProcessor>();
    }

    public IPaymentValidator CreatePaymentValidator()
    {
        return _serviceProvider
            .GetRequiredService<StripePaymentValidator>();
    }
}

وتسجل الـ Services:

builder.Services.AddScoped<StripePaymentProcessor>();
builder.Services.AddScoped<StripePaymentValidator>();
builder.Services.AddScoped<IPaymentFactory, PaymentFactory>();
ملحوظة مهمة: المثال ده للتوضيح فقط، والاختيار هنا ثابت على Stripe. في مشروع Production ممكن تستخدم إعدادات أو Strategy أو Keyed Services لاختيار الـ Provider، وتتجنب استخدام IServiceProvider بشكل عشوائي في كل مكان (Service Locator).

خامسًا: إمتى أستخدم كل Pattern؟

استخدم Simple Factory لما:

  • عندك عدد قليل من الأنواع.
  • عندك مكان مركزي مسؤول عن الإنشاء.
  • عايز حل بسيط بدون تعقيد الـ Inheritance.

استخدم Factory Method لما:

  • عندك أنواع مختلفة من المنتجات.
  • عايز كل نوع يكون له Creator خاص بيه.
  • عايز تضيف أنواع جديدة بدون تعديل الـ Creator الأساسي.

استخدم Abstract Factory لما:

  • عندك مجموعات من المنتجات مرتبطة ببعض.
  • لازم المنتجات اللي بتتعمل مع بعض تكون متوافقة.
  • عندك Providers أو Platforms مختلفة، وكل واحدة بتوفر مجموعة Implementations.

سادسًا: اختبر فهمك

عايز أتأكد إنك فهمت الفرق، جرب تجاوب على الأسئلة دي. اختار إجابة لكل سؤال، وبعدها اضغط «تصحيح الإجابات».

1. عندك NotificationFactory فيها Switch بتنشئ Email أو SMS أو WhatsApp. ده مثال على إيه؟
2. عندك Base Creator فيه CreateDocument()، وكل Subclass بتعمل Override وترجع نوع Document مختلف. ده إيه؟
3. عندك StripeFactory بتنشىء StripeProcessor وStripeValidator، وعندك PayPalFactory بتنشىء PayPalProcessor وPayPalValidator. ده إيه؟

الخلاصة والنصيحة

متَحفظش شكل الكود بس. ركز على الأسئلة دي في كل Pattern:

  1. مين المسؤول عن إنشاء الـ Object؟
  2. مين بيحدد نوع الـ Object؟
  3. هل بننشئ Object واحد ولا عائلة Objects؟

لو عرفت تجاوب على التلات أسئلة دول، هتعرف تفرق بين Simple Factory وFactory Method وAbstract Factory بسهولة.
